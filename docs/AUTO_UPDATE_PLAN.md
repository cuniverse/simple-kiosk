# Simple Kiosk Git 기반 자동 업데이트 계획

> 상태: 설계 검토 단계 — 아직 구현되지 않음  
> 1차 대상: Windows 키오스크 배포본  
> 업데이트 원본: GitHub Releases

## 1. 목적

운영 중인 키오스크가 GitHub에 배포된 새 버전을 안전하게 확인하고 설치할 수 있게 한다.
업데이트 과정에서 운영자가 변경한 메뉴, URL, 화면 보호기 설정과 사용자 미디어를
보존하면서 새 버전에 추가된 기본 설정은 자동으로 반영해야 한다.

자동 업데이트는 각 키오스크의 관리자 설정에서 켜거나 끌 수 있어야 한다. 설치 실패,
파일 손상 또는 새 버전 실행 실패 시에는 직전 정상 버전으로 자동 복구해야 한다.

## 2. 기본 원칙

- 설치 PC에서 소스 저장소를 `git pull`하거나 Flutter 빌드를 실행하지 않는다.
- Git 저장소의 태그로 생성한 GitHub Release ZIP을 업데이트 단위로 사용한다.
- 프로그램 파일과 운영 데이터를 물리적으로 분리한다.
- 실행 중인 EXE와 DLL에 일부 파일만 덮어쓰지 않는다.
- 새 버전은 별도 폴더에 완전히 준비한 후 현재 버전 포인터를 전환한다.
- 운영 설정과 업데이트 정책은 앱 버전 교체 및 롤백의 영향을 받지 않는다.
- 자동 업데이트 기본값은 `OFF`로 하여 기존 운영 장비가 예고 없이 갱신되지 않게 한다.
- 키오스크가 사용 중일 때는 설치하지 않는다.

## 3. 현재 구조와 해결할 문제

현재 앱은 `assets/config/menu.json`을 Flutter `rootBundle`에서 직접 읽는다. Windows
배포본에서는 다음 위치의 파일을 운영자가 직접 수정한다.

```text
<설치 폴더>\data\flutter_assets\assets\config\menu.json
```

Windows 패키징 스크립트는 빌드 결과의 `data` 폴더 전체를 ZIP에 포함한다. 새 패키지를
기존 설치 폴더에 덮어쓰면 운영자가 수정한 `menu.json`과 사용자 이미지가 사라질 수
있다. 반대로 기존 `menu.json` 전체를 새 버전에 복사하면 새로 추가된 기본 설정과 메뉴가
반영되지 않을 수 있다.

따라서 자동 업데이트 전에 다음 구조 변경이 선행되어야 한다.

1. 앱 기본 설정과 운영자 변경 설정 분리
2. 설정 병합 및 스키마 마이그레이션 도입
3. 프로그램과 운영 데이터 저장 위치 분리
4. 버전별 설치와 롤백이 가능한 실행 구조 도입

## 4. 목표 디렉터리 구조

```text
C:\ProgramData\SimpleKiosk\
  current.json                     # 현재/직전 정상 버전 포인터
  config\
    menu.override.json             # 운영자가 변경한 값만 저장
    update-policy.json             # 자동 업데이트 On/Off 및 운영 정책
  media\                           # 운영자가 추가한 이미지/동영상/아이콘
  state\
    update-state.json              # 확인/다운로드/설치 결과와 재시도 상태
    last-good-config.json          # 마지막으로 파싱에 성공한 최종 설정
  logs\
    updater.log
  downloads\                       # 다운로드 중인 임시 파일
  versions\
    1.2.0\                         # 완전한 버전별 실행 패키지
    1.3.0\
```

앱의 기본 설정은 각 버전 패키지 안에 `menu.defaults.json`으로 포함한다. 운영 데이터는
`C:\ProgramData\SimpleKiosk` 아래에만 저장하고 버전 폴더에는 기록하지 않는다.

## 5. 설정 보존 및 새 설정 반영

### 5.1 최종 설정 계산

앱 시작 시 다음 순서로 실제 설정을 만든다.

```text
새 버전 menu.defaults.json
  + menu.override.json
  + 필요한 스키마 마이그레이션
  = 실제 적용 설정
```

운영 설정은 전체 `menu.json` 복사본이 아니라 운영자가 변경한 값만 기록한다. 따라서 새
버전에서 설정 키가 추가되면 오버라이드에 같은 키가 없는 한 새 기본값이 자동 적용된다.

### 5.2 오버라이드 형식 초안

```json
{
  "schemaVersion": 1,
  "layout": {
    "toolbarAutoHideSec": 20
  },
  "idle": {
    "timeoutSec": 120
  },
  "items": {
    "overrides": {
      "home": {
        "url": "https://custom.example.com"
      }
    },
    "additions": [],
    "disabledIds": [],
    "order": []
  }
}
```

### 5.3 병합 규칙

- `layout`, `idle` 같은 객체는 키 단위로 재귀 병합한다.
- 오버라이드에 없는 새 키는 새 버전 기본값을 사용한다.
- 오버라이드에 있는 키는 운영자 값을 우선한다.
- `null`은 키 삭제가 아니라 명시적인 기본값 복원으로 정의한다.
- 메뉴는 배열 위치가 아닌 변하지 않는 `items[].id`를 기준으로 병합한다.
- 기본 메뉴의 URL·제목 등을 운영자가 수정한 경우 해당 필드만 보존한다.
- 새 버전에 추가된 기본 메뉴는 `disabledIds`에 없는 한 기본 순서에 맞춰 추가한다.
- 운영자가 추가한 메뉴는 `additions`에 완전한 항목으로 저장하고 업데이트 후에도 유지한다.
- 새 버전에서 제거된 기본 메뉴의 불완전한 오버라이드는 비활성 항목으로 기록하고 경고한다.
- 메뉴 순서를 직접 지정하지 않았다면 새 기본 순서를 사용한다.
- 사용자 미디어 경로는 외부 `media` 폴더를 기준으로 해석한다.
- 병합 또는 파싱 실패 시 `last-good-config.json`으로 복구하고 오류를 기록한다.

### 5.4 기존 설치의 최초 마이그레이션

첫 자동 업데이트 시 기존 설치 폴더의 `menu.json`을 그대로 덮어쓰지 않는다.

1. 설치된 앱 버전을 확인한다.
2. 해당 버전의 원본 기본 설정과 현재 운영 `menu.json`을 비교한다.
3. 차이만 `menu.override.json`으로 변환한다.
4. 기존 설정과 사용자 이미지를 날짜가 포함된 백업 폴더에 복사한다.
5. 새 기본 설정과 생성된 오버라이드를 병합하고 검증한다.
6. 검증에 성공한 경우에만 새 버전을 활성화한다.

기존 버전의 원본 기본 설정을 찾을 수 없는 경우에는 자동 추정을 하지 않고 전체 설정을
백업한 뒤 관리자 확인이 필요한 상태로 남긴다.

## 6. 자동 업데이트 On/Off 정책

업데이트 정책은 메뉴 설정과 분리해 다음 파일에 저장한다.

```text
C:\ProgramData\SimpleKiosk\config\update-policy.json
```

초기 형식은 다음과 같다.

```json
{
  "schemaVersion": 1,
  "enabled": false,
  "channel": "stable",
  "checkIntervalHours": 6,
  "installWhenIdle": true,
  "installWindow": {
    "start": "02:00",
    "end": "05:00"
  }
}
```

### OFF

- 예약된 버전 확인, 다운로드, 자동 설치를 수행하지 않는다.
- 이미 다운로드한 버전도 자동 설치하지 않는다.
- 관리자의 `지금 업데이트 확인`과 `지금 설치`는 사용할 수 있다.
- 현재 버전, 운영 설정과 사용자 데이터는 그대로 유지한다.

### ON

- 지정된 주기로 새 GitHub Release를 확인한다.
- 사용 중에는 다운로드까지만 허용하고 설치하지 않는다.
- `installWhenIdle`이 켜져 있으면 화면 보호기 상태에서만 설치를 시작한다.
- 설치 가능 시간대가 지정되어 있으면 화면 보호기 상태와 시간 조건을 모두 만족해야 한다.
- 설치 직전에 앱을 정상 종료하고 별도 업데이트 실행기가 파일을 전환한다.

### 관리자 UI

일반 사용자가 변경하지 못하도록 PIN으로 보호된 관리자 화면에 둔다.

```text
자동 업데이트       [ ON / OFF ]
업데이트 채널       [ stable ]
확인 주기           [ 6시간 ]
설치 가능 시간      [ 02:00 ~ 05:00 ]
현재 버전           1.2.0
사용 가능한 버전    1.3.0
마지막 확인         2026-08-13 14:30
업데이트 상태       다운로드 완료 / 설치 대기
[지금 업데이트 확인] [지금 설치]
```

정책 저장은 임시 파일에 쓴 뒤 이름을 교체하는 원자적 방식으로 처리한다. 앱과 업데이트
실행기는 같은 정책 파일을 읽어야 하며, 업데이트 패키지는 이 파일을 포함하거나
덮어쓰면 안 된다.

## 7. GitHub Release 구성

현재 태그 기반 GitHub Actions 릴리스 흐름을 확장한다. 각 Release에는 다음 파일을
게시한다.

```text
simple-kiosk-windows-<version>.zip
update-manifest.json
```

Manifest 초안:

```json
{
  "schemaVersion": 1,
  "version": "1.3.0",
  "channel": "stable",
  "publishedAt": "2026-08-13T00:00:00Z",
  "minimumUpdaterVersion": "1.0.0",
  "configSchemaVersion": 1,
  "package": {
    "file": "simple-kiosk-windows-1.3.0.zip",
    "sha256": "<ZIP SHA-256>"
  }
}
```

버전 비교는 문자열 비교가 아니라 Semantic Versioning 규칙을 사용한다. 정식 운영
장비의 `stable` 채널에서는 prerelease와 draft Release를 제외한다.

## 8. 업데이트 실행 절차

1. 로컬 정책이 `enabled=true`인지 확인한다.
2. GitHub Release의 manifest를 조회한다.
3. 현재 버전보다 새로운 안정 버전인지 확인한다.
4. ZIP을 `downloads` 폴더에 내려받는다.
5. SHA-256, ZIP 경로 안전성, 필수 파일 존재 여부를 검증한다.
6. 임시 버전 폴더에 압축을 해제한다.
7. 새 기본 설정과 운영 오버라이드를 병합해 사전 검증한다.
8. 설치 조건이 될 때까지 `설치 대기` 상태로 둔다.
9. 앱에 종료를 요청하고 별도 업데이트 실행기가 프로세스 종료를 확인한다.
10. 새 버전 폴더를 `current.json`의 현재 버전으로 전환한다.
11. 앱을 실행하고 일정 시간 동안 시작 성공 신호를 기다린다.
12. 성공하면 새 버전을 정상 버전으로 확정한다.
13. 실패하면 직전 정상 버전으로 포인터를 되돌리고 재실행한다.

네트워크 오류는 앱 실행을 막지 않아야 한다. 실패 시 지수 백오프로 재시도하며 동일한
버전의 반복 설치 실패 횟수에는 상한을 둔다.

## 9. 실행 구성 요소

### Kiosk Launcher

- 항상 고정된 위치에서 실행된다.
- `current.json`을 읽어 현재 버전의 `simple_kiosk.exe`를 시작한다.
- 현재 버전이 손상된 경우 직전 정상 버전을 시작한다.

### Kiosk App

- 현재 버전과 업데이트 상태를 관리자 화면에 표시한다.
- 자동 업데이트 정책을 변경한다.
- 화면 보호기 진입 및 설치 가능 상태를 업데이트 실행기에 알린다.
- 설치 요청을 받은 경우 세션과 설정을 저장하고 정상 종료한다.

### Kiosk Updater

- GitHub Release 확인, 다운로드, 검증과 설치를 담당한다.
- 앱과 별도 프로세스로 실행되어 Windows 파일 잠금을 피한다.
- 운영 설정과 사용자 미디어에는 쓰지 않는다.
- 설치 결과와 오류를 `update-state.json` 및 로그에 기록한다.

업데이트 실행기 자체를 갱신해야 할 경우에는 새 실행기를 별도 이름으로 배치한 뒤
Launcher가 다음 시작 시 교체하는 2단계 갱신을 사용한다.

## 10. 보안 및 안정성

- HTTPS GitHub API와 GitHub Release URL만 허용한다.
- ZIP 전체의 SHA-256을 manifest와 대조한다.
- 가능하면 Windows 실행 파일에 코드 서명을 적용한다.
- 압축 해제 시 절대 경로, `..` 및 설치 루트 밖 경로를 거부한다.
- 관리자 PIN은 평문으로 저장하지 않는다.
- 업데이트 정책 및 설정 폴더는 일반 키오스크 사용자가 수정하지 못하게 ACL을 설정한다.
- 비공개 저장소를 사용할 경우 장기 GitHub 토큰을 키오스크에 평문 저장하지 않는다.
- 설치 전후 설정 백업과 최근 정상 버전을 최소 1개 유지한다.
- 로그에 토큰, 쿠키, URL 쿼리의 민감값을 기록하지 않는다.

## 11. 단계별 구현 계획

### 1단계 — 외부 설정과 병합

- `menu.defaults.json`과 `menu.override.json` 분리
- 외부 설정 경로 결정 및 생성
- 객체 재귀 병합과 메뉴 ID 기반 병합 구현
- 설정 스키마 버전 및 마이그레이션 인터페이스 추가
- 마지막 정상 설정 복구 추가
- 기존 `menu.json` 마이그레이션 도구 작성

완료 기준: 새 기본 키와 메뉴가 추가되어도 운영자의 URL·색상·미디어 설정이 유지된다.

### 2단계 — 릴리스 메타데이터

- Windows ZIP SHA-256 생성
- `update-manifest.json` 생성 및 Release 첨부
- 앱/패키지 버전을 단일 원본에서 생성
- stable/prerelease 채널 판별 규칙 추가

완료 기준: 설치된 앱이 최신 Release의 버전과 무결성을 판별할 수 있다.

### 3단계 — 업데이트 확인 및 관리자 정책

- `update-policy.json` 모델과 원자적 저장 구현
- 기본 OFF 정책 적용
- 관리자 PIN 보호 화면 추가
- 자동 확인, 수동 확인과 상태 표시 구현
- OFF 전환 시 예약 작업과 설치 대기 취소

완료 기준: 장비별로 자동 업데이트를 켜고 끌 수 있고 재시작 후에도 상태가 유지된다.

### 4단계 — Launcher와 Updater

- 고정 Launcher와 별도 Updater 구현
- 버전별 다운로드, 검증, 압축 해제와 포인터 전환
- 앱 정상 종료와 재시작 프로토콜 구현
- 시작 성공 신호 및 자동 롤백 구현

완료 기준: 실행 중인 파일을 덮어쓰지 않고 새 버전을 설치하며 실패 시 이전 버전으로
돌아간다.

### 5단계 — 무인 운영 연동

- 화면 보호기 상태와 설치 가능 시간대 연동
- 네트워크 실패 백오프와 중단된 다운로드 재개
- 반복 실패 차단 및 관리자 알림
- 오래된 버전/다운로드 정리 정책 적용

완료 기준: 실제 사용 중인 화면을 중단하지 않고 무인 시간에 업데이트된다.

### 6단계 — 문서와 점진 배포

- 설치·업데이트·복구 관리자 문서 작성
- 수동 복구 도구와 진단 로그 내보내기 제공
- 테스트 장비 → 제한된 운영 장비 → 전체 장비 순으로 배포

완료 기준: 운영자가 개발 도구 없이 업데이트 상태 확인, 중지, 재시도와 복구를 수행할
수 있다.

## 12. 테스트 계획

### 설정 병합

- 운영자가 수정한 scalar 값 보존
- 새 기본 키 자동 추가
- 메뉴 ID 기준 URL 변경 보존
- 새 기본 메뉴 자동 추가
- 운영자 추가 메뉴 보존
- 제거된 기본 메뉴와 orphan override 처리
- 구버전 스키마 순차 마이그레이션
- 손상된 JSON에서 마지막 정상 설정 복구

### 업데이트

- 최신 버전 없음
- 다운로드 중 네트워크 단절 및 재시도
- SHA-256 불일치 파일 거부
- 손상되거나 필수 DLL이 없는 패키지 거부
- 앱 실행 중 설치 보류
- 화면 보호기 진입 후 설치
- 업데이트 OFF 상태에서 확인·다운로드·설치 미실행
- 다운로드 후 OFF 전환 시 자동 설치 취소
- 새 버전 시작 실패 후 자동 롤백
- 설치 도중 전원 종료 후 정상 버전 재시작

### 운영 데이터

- 업데이트 및 롤백 후 메뉴 설정 유지
- 사용자 이미지와 동영상 유지
- WebView 쿠키·캐시가 패키지에 포함되지 않음
- 여러 번 연속 업데이트 후 설정 중복 또는 유실 없음

## 13. 구현 전 결정할 항목

- GitHub 저장소를 공개로 유지할지, 별도 배포 저장소를 사용할지
- 자동 업데이트 기본값을 모든 신규 설치에서도 OFF로 유지할지
- 관리자 인증 방식(PIN, Windows 계정 또는 별도 관리 도구)
- 설치 가능 시간대의 기본값
- 운영자 추가 메뉴와 제거된 기본 메뉴의 세부 병합 정책
- 보관할 이전 버전 수와 로그 보존 기간
- Windows 코드 서명 인증서 적용 시점
- macOS 및 Android 자동 업데이트를 같은 범위에 포함할 시점

## 14. 1차 권장 범위

첫 구현은 Windows와 `stable` 채널로 제한한다. 자동 업데이트 기본값은 OFF로 두고,
관리자가 켠 장비만 GitHub Release를 확인한다. 운영 설정 분리와 병합을 먼저 완료한 뒤
업데이트 설치 기능을 연결해야 한다. 설정 분리 없이 자동 설치부터 구현하면 운영 설정
유실 위험을 제거할 수 없다.
